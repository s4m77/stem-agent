# Task 2

The development sof background agents is much more capable than ordinary chatbots. Systems such as Codex and Claude Code can inspect codebases, edit files, run tests, and work asynchronously in sandboxed environments. That is definitely a step forward, but does not yet give us a complete AI software engineer.

The central limitation is that current LLM-based agents are not rational agents in the classical sense. A rational agent should choose actions by estimating possible outcomes and selecting the action that maximizes expected utility for the user. An LLM does not natively do that. Its core mechanism is to generate likely continuations conditioned on a prompt, context window, and training distribution. When wrapped in a loop with tools, it can imitate planning: “I should inspect the repo,” “I should run tests,” “I should fix the failing function.” But imitation of deliberation is not the same as stable expected-utility maximization.

This difference matters most on open-ended tasks. For narrow tasks, the imitation is often enough. If the environment is constrained, the tool calls are simple, and success is easy to verify, an LLM agent can look genuinely autonomous. But a complete software engineer must make decisions under uncertainty: which bug matters, which tradeoff is acceptable, which abstraction will survive future changes, whether a failing test indicates a real bug or a bad test, whether a change is safe to deploy, and whether the user’s request is actually underspecified.

Current systems still struggle with long horizons. They lose track of constraints, overfit to local fixes, misread repository structure, trust incomplete tests, and produce plausible but wrong explanations. This is visible in software benchmarks: realistic long-horizon engineering tasks remain far from solved, as seen in SWE-Bench Pro (leading agents show mediocre performance on complex enterprise-level issues). That gap is not only about code syntax; it is about planning, context management, causal reasoning, and verification.

A second bottleneck is self-evaluation. Human engineers do not just write code; they check whether the change is conceptually right. Agents can run tests, but tests are not complete specifications. Many real failures are architectural, product-level, or operational. An agent that only optimizes for “tests pass” may introduce technical debt, security problems, performance regressions, or incorrect behavior outside the test suite.

A third bottleneck is authority. Fully autonomous agents need permission to act, but real actions have costs. They can delete files, leak secrets, spend money, deploy broken software, or make irreversible product decisions. That is why current agentic coding tools still rely on sandboxes, review flows, auto-approval boundaries, and human interruption. The problem is not simply that models are not smart enough; it is that autonomy without reliable judgment is unsafe.

So what stops us from building a complete AI software engineer is a stack of missing capabilities: stable objectives, calibrated beliefs, causal world models, long-horizon memory, reliable self-critique, grounded tool use, secure execution, and accountability. Better models will help, but prompting alone cannot close the gap. A useful autonomous engineer needs an “immune system”: verification, rollback, uncertainty estimation, permission boundaries, and human escalation when the expected utility is unclear.

In my opinion, the realistic near-term path is supervised autonomy: agents that do increasingly large chunks of work, but inside constrained environments with measurable feedback and human review. The goal is to move the human from typing every line to setting objectives, judging tradeoffs, and approving irreversible actions. A complete AI software engineer will require not only stronger language models, but agent architectures that can actually decide, verify, and take responsibility for consequences.
